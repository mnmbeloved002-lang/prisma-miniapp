# PROJECT CONSTITUTION v3 (2025–2026)

## 0. Назначение документа

Этот документ — единый источник истины по:

- принципам инженерной работы (Кодекс),
- архитектуре miniapp и контент-пайплайна,
- контурам качества и безопасности (L0–L2+nightly),
- требованиям к коду (Кодекс качества 2026),
- процессу проверки готовности (ERL-100).

Любое решение по проекту сверяется с этим документом.

## 1. Кодекс инженера и режим работы

### 1.1. Роль UEC и контекст

- Режим: **SOLO_DEVELOPER + ZERO_COST**.
- Ядро платформы: GitHub + GitHub Actions + Vercel + бесплатные OSS-инструменты.
- UEC объединяет роли:
  - Tech Lead / Staff
  - Senior Backend / Platform
  - DevOps / SRE
  - Senior Frontend
  - QA Automation / SDET
  - Security / AppSec
  - Product Manager / Ops
  - UX / UI Designer
  - Technical Writer / DX

### 1.2. Базовые заповеди

1. **Один шаг — один результат.**  
   Любое изменение атомарно. Переход к следующему шагу запрещён, пока не пройден DoD.
2. **Проверка — закон, не формальность.**  
   Definition of Done включает: код, тесты, CI, docs. Без этого работа не считается завершённой.
3. **История — совесть инженера.**  
   Каждый коммит описывает конкретное изменение. Бессмысленные сообщения запрещены.
4. **main — неприкасаемая ось.**  
   Ветка `main` обновляется только через PR с зелёными гейтами.
5. **Код как архитектура.**  
   Каждый модуль независим и заменяем. Добавление/удаление не ломает систему.
6. **Автоматизация вместо ручного труда.**  
   Всё повторяемое выносится в скрипты/CI.
7. **Чистота выше скорости.**  
   Быстро = предсказуемо, повторяемо, с зелёным CI.
8. **Сознательная инженерия.**  
   Не «написать код», а построить систему, живущую годами.
9. **Никаких долгов.**  
   Любая фича/фикс доводится до конца в одном цикле: код → тесты → CI → docs. «Сделаем потом» оформляется задачей и закрывается.

### 1.3. Иерархия источников истины

1. **Фундамент (L4-экспертиза)** — современные практики по всем 9 ролям.
2. **Стратегия (Намерение)** — настоящий документ (Конституция/Кодекс).
3. **Тактика (Реализация)** — ERL-100 чек-лист + конкретные YAML/скрипты/конфиги в репозитории.

### 1.4. Ветки и процесс

- Ветки:
  - `main` — только стабильные релизы, строго через PR.
  - `dev` — рабочая ветка (единственная линия разработки).
- Процесс:
  - Работа ведётся в `dev`.
  - Релиз: PR `dev → main` с обязательными гейтами:
    - `Content Compliance Gates`
    - `1) Verify (Lint + Types + Build + Tests + Audit + Size + LHCI)`
- Force-push в `main`/`dev` запрещён настройками веток и Кодексом.

### 1.5. Иерархия приоритетов

1. **Безопасность и конфиденциальность**
   - защита данных пользователей;
   - защита ключей, токенов, секретов;
   - отсутствие утечек и инъекций важнее любой фичи.

2. **Целостность и надёжность данных**
   - `news.json` и другие артефакты никогда не должны быть «битые»;
   - бэкапы и возможность rollback важнее скорости выката.

3. **Наблюдаемость**
   - логи, метрики, алерты;
   - способность быстро обнаружить и расследовать проблему важнее скорости изменения.

4. **Качество кода и UX**
   - тесты, читаемость, предсказуемость поведения;
   - удобство для пользователя и поддерживаемость.

5. **Скорость разработки и релиза**
   - ускорение допустимо только если не нарушены пункты 1–4.

Любое решение, которое нарушает этот порядок (например, «ускорим релиз ценой временного отключения проверок безопасности»), требует отдельного ADR с явным обоснованием.

## 2. Архитектура платформы

### 2.1. Слои и зависимости

Логические слои:

- `ui` — компоненты интерфейса miniapp.
- `application` — сценарии, оркестрация, кэш/букмарки.
- `domain` — доменные модели и правила (news, filters, url-логика).
- `infrastructure` — API-клиенты, адаптеры к Telegram, сети, storage.

Требования:

- Зависимости только сверху вниз: `ui → application → domain → infrastructure`.
- `domain` не знает о `ui`/`infrastructure`.
- Вход/выход всех слоёв описан типами и runtime-контрактами (Zod/Ajv).

### 2.2. Управление состоянием (frontend)

- Глобальное состояние:
  - фильтры и сортировка ленты,
  - флаги отображения (например, showBookmarks),
  - режимы чтения/прослушивания.
- Data-кэш (загруженные данные, Статьи) отделён от UI-состояния.
- Локальный `useState` — только для чисто локальных деталей (модалки, input-состояние).
- Вся бизнес-логика состояния тестируется unit/IT-тестами, без привязки к конкретным компонентам.

### 2.3. Zero-Mutation и Event-Driven

- Иммутабельность по умолчанию:
  - Не мутируем параметры и «чужие» объекты.
  - Используем `readonly` в TypeScript там, где возможно.
- Побочные эффекты (I/O: fetch, storage, логирование) вынесены в отдельные функции/модули.
- Внутренние взаимодействия проектируются как «событие → реакция»:

  - пример: «новости загружены» → «обновить ленту + пересчитать метрики»;
  - пример: «кликнули “слушать”» → «запустить TTS-цепочку».

### 2.4. Внешние границы и контракты

- Все входящие данные (REST/API/файлы) проходят через runtime-валидацию:
  - `news.json` и другие данные валидируются Zod/Ajv-схемами.
- TypeScript-типы — **не контракт**, а помощь разработчику. Настоящий контракт — Zod/Ajv-схема.
- Любое расширение схемы сопровождается:
  - изменением схемы в `docs/schema`,
  - обновлением валидаторов,
  - тестами на валид/невалид примеры.

## 3. Фазы 0–2 (контур зрелости)

### 3.1. Фаза 0 — Фундамент (индустриальная надёжность)

Цели:

- Репозиторий, ветки, CI, минимально надёжный фронт.
- Контракт `news.json` + валидация + backup/rollback.

Результаты Фазы 0:

- Настроены ветки `main`/`dev` и защита `main`.
- Описан и реализован контракт `news.json` (docs/schema + Zod/Ajv + `scripts/validate-news*`).
- Есть локальная и CI-валидация `news.json`.
- Реализованы бэкапы и быстрый rollback `news.json` (RTO ≤ 5 минут).
- Сформирован базовый L0-контур (lint, types, unit-tests, build, size-limit).

### 3.2. Фаза 1 — UI/UX miniapp

Цели:

- Стабильный интерфейс miniapp (Telegram/Web) с учётом UX и a11y.
- Компоненты и состояние не ломаются при расширении.

Результаты Фазы 1:

- Главный shell miniapp + ключевые экраны:
  - лента новостей,
  - карточка,
  - закладки/фильтры,
  - режимы «читать/слушать».
- Архитектура UI разведена по слоям (`ui`, `application`).
- Реализованы критичные e2e-сценарии (Playwright):
  - лента → карточка → назад,
  - управление закладками,
  - чтение/прослушивание,
  - ошибки сети.
- Включены визуальные и a11y-проверки.

### 3.3. Фаза 2 — Контент-пайплайн (zero-touch ingestion)

Цели:

- Весь контент `news.json` обновляется автоматизированно.
- Любое изменение проходит через контракт, гейты и бэкап.

Результаты Фазы 2:

- Описаны источники новостей и правила нормализации (docs/fetch, docs/normalize).
- Реализованы ingestion-скрипты (fetch/normalize) и Content Compliance gate.
- Контент-PR создаётся автоматически (или минимально вручную, по строгой политике).
- При merge контентного PR:
  - считается hash итогового `news.json`,
  - записывается цепочка целостности (`docs/checksums/chain.log`),
  - создаётся бэкап.
- Включены DQM-правила (data quality) и observability (метрики/алерты по пайплайну).
- Проведён UAT Фазы 2 (docs/uat).

## 4. Контуры качества и безопасности (L0–L2 + Nightly)

### 4.1. L0 — быстрый контур (каждый PR)

L0-контур запускается на каждый PR, минимум для `main`, опционально для `dev`.

Состав:

- `pnpm lint` — ESLint + typescript-eslint + плагины (import, security, react-hooks и др.).
- `pnpm typecheck` — строгий TypeScript (`tsc --noEmit`).
- `pnpm test:cov` — Vitest + покрытие.
- `pnpm pkg:lint` — `npm-package-json-lint`.
- `pnpm audit` / OSV-Scanner — проверки зависимостей.
- `pnpm build` — сборка.
- `pnpm size` — Size-Limit, контроль веса бандла.
- `pnpm lhci` — Lighthouse CI по `dist/`.

Гейт:

- Без зелёного L0 merge в `main` запрещён.

### 4.2. L1 — расширенный контур (e2e, a11y, visual, security)

L1 может запускаться на каждый PR в `main` или по расписанию/по кнопке.

Состав:

- e2e:
  - `pnpm e2e:smoke` — ключевые сценарии.
  - `pnpm e2e:a11y` — Playwright + axe.
  - `pnpm e2e:visual` — скриншотные дифы.
- Security:
  - OSV-Scanner,
  - Semgrep (security + best practices),
  - Gitleaks (секреты).
- Content Compliance:
  - проверка контракта данных,
  - allow-list файлов,
  - лимит diff,
  - обработка кейса «0 новостей».

Гейт:

- Нарушения Content Compliance и критичные security-найды блокируют PR.

### 4.3. L2 / Nightly — глубокий контур

Состав:

- Stryker — мутационное тестирование ключевых модулей:
  - URL/share-логика,
  - API-клиент и кэш,
  - валидаторы данных.
- k6 — лёгкий нагрузочный smoke (10–30 rps, 1–3 минуты).
- Syft + Grype — SBOM + поиск уязвимостей.
- Knip / dep-cruiser / depcheck — поиск мёртвого кода и плохих зависимостей.
- Lighthouse CI в режиме nightly (тренд метрик).
- Опционально: Sitespeed.io, ZAP Baseline, CodeQL (если оправдано).

Результаты ночного контура:

- При критичных отклонениях:
  - блокируется следующий релиз,
  - создаются задачи/issue,
  - обновляются метрики/отчёты в docs/ops.

## 5. Кодекс качества кода 2026

Этот раздел фиксирует правила на уровне кода.

### 5.1. Архитектура и контракты

- Все внешние границы (API, файлы, сторонние сервисы) валидируются runtime-схемами (Zod/Ajv).
- Модули имеют явные входы/выходы; не полагаются на глобальные синглтоны.
- Dependency-Cruiser (и/или аналоги) контролирует архитектурные правила:
  - слой `domain` не тянет `ui`/`infrastructure`;
  - нет циклических зависимостей между модулями.

### 5.2. Правила написания функций

- Функция делает **одну вещь** (SRP).
- По умолчанию — чистая: без побочных эффектов, детерминированная.
- Вложенность не более двух уровней; предусловия срабатывают через guard-clauses (ранний выход).
- Асинхронность:
  - нет `await` внутри `Array.prototype.map` / `forEach` / циклов без причины;
  - используется `Promise.all / Promise.allSettled`, когда возможна параллельность.
- Иммутабельность:
  - параметры не мутируются;
  - объекты защищаются `readonly`, копирование — через безопасные операции.

### 5.3. Ошибки, Result и Option

- В доменной логике не используется `throw`/`try-catch` как обычный поток управления.
- Вместо этого — `Result`/`Option`-паттерны:
  - `Ok(value) / Err(error)`,
  - `Some(value) / None`.
- «Несчастный путь» (sad path) читается так же прозрачно, как успешный:

  - нет скрытых «провалов» через `null/undefined`,
  - ошибки типизированы и обрабатываются явно.

### 5.4. Метрики сложности

- Цикломатическая сложность одной функции ≤ 10.
- Когнитивная сложность ≤ 15.
- Maintainability-индекс должен быть высоким; функции, выходящие за пороги, подлежат рефакторингу.
- В CI запускается анализ сложности, и критические превышения либо:
  - блокируют PR,
  - либо создают задачи на рефакторинг.

### 5.5. Тесты и мутации

- Тестирование строится по принципу «Testing Trophy»:
  - упор на integration-тесты и e2e для критичных сценариев;
  - unit-тесты — для чистой логики.
- Мутационное тестирование (Stryker) используется для:
  - оценки реальной силы тестов,
  - повышения покрытия смысловых ветвей.
- Цель — mutation-score не ниже согласованного порога (70–80% для ключевых модулей).

### 5.6. Инструменты и автоматизация

Минимальный набор для код-качества:

- TypeScript (strict),
- ESLint (+ плагины),
- Vitest,
- @testing-library/react + user-event,
- Playwright,
- axe / axe-playwright,
- Zod/Ajv,
- Size-Limit,
- Lighthouse CI,
- OSV-Scanner,
- Semgrep,
- Gitleaks,
- Syft + Grype,
- Stryker,
- k6,
- Knip / dependency-cruiser,
- Husky + lint-staged + commitlint.

Все они интегрированы в:

- `package.json` (скрипты),
- GitHub Actions (workflow),
- ERL-100 чек-лист (пункты установки и проверки).

## 6. Observability и эксплуатация

### 6.1. Логирование

- Все критичные модули (ingestion, compliance, backup/restore, API-эндпоинты) используют структурированный логгер (JSON-формат).
- В логах фиксируются:
  - timestamp (UTC),
  - уровень (info/warn/error),
  - компонент/модуль,
  - request-id/trace-id,
  - ключевые параметры (источник, id новости и т.п.).
- Логи не содержат секретов; чувствительные данные маскируются.

### 6.2. Метрики и дашборды

- Определены ключевые метрики контент-пайплайна:
  - TTFPR (time-to-fetch-PR),
  - объём `news.json`,
  - доля пустых превью,
  - число дублей,
  - число ошибок ingestion,
  - число «пустых прогонов».
- Метрики собираются при каждом прогоне ingestion/Compliance.
- Есть дашборд (или минимальный отчёт), где эти метрики видны во времени.

### 6.3. Алерты

- Критические события:
  - `0 новостей`, когда ожидается >0,
  - резкий скачок объёма `news.json`,
  - серия ошибок ingestion,
  - DQM-статус «красный»
  — триггерят алерт в выделенный канал (например, Telegram-бот).
- Для алертов прописаны пороги (Warning/Critical) и runbook реакции.

### 6.4. Инциденты и постмортем

- Любой инцидент (битый контент, деградация, security-событие) фиксируется постмортемом:
  - факты,
  - как обнаружили,
  - root cause,
  - почему не поймали раньше,
  - что изменено в коде/тестах/наблюдаемости/процессах.
- Важные архитектурные решения оформляются как ADR.

## 7. ERL-100: чек-лист готовности

- В `docs/ERL100-CHECKLIST.md` хранится полный чек-лист из пунктов 1…N (ERL-100).
- Этот чек-лист:
  - разбивает систему на атомарные проверки,
  - фиксирует статус `✅ / 🟡 / ⬜` для каждого пункта,
  - служит операционным инструментом до/после релиза.

Правило работы:

- Одна итерация = один пункт/малый блок чек-листа.
- Для каждого пункта:
  - есть фактическая проверка (команды/файлы),
  - есть вердикт,
  - есть фиксация результата (в ERL-100).

## 8. Эволюция Конституции

- Конституция и Кодекс качества пересматриваются регулярно (например, раз в квартал).
- Любое существенное изменение:
  - оформляется через PR,
  - сопровождается ADR, если влияет на архитектуру/процессы,
  - влечёт обновление ERL-100, если меняются критерии готовности.

Этот документ имеет более высокий приоритет, чем любые устные договорённости или незафиксированные решения. Если код, конфигурация или процесс расходятся с Конституцией, это считается дефектом и подлежит исправлению.
