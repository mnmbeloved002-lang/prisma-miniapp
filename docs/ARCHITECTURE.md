# Prisma Miniapp — Architecture Overview (v2025-11)

## 1. Цель документа

Кратко зафиксировать архитектуру проекта, чтобы любой инженер мог за 5–10 минут понять:
- из чего состоит система;
- как данные проходят путь от источников до miniapp;
- какие слои кода за что отвечают;
- какие инварианты должны сохраняться.

## 2. Общий контекст

- Клиент: Telegram WebApp + обычный браузер (desktop/mobile).
- Хостинг фронта: Vercel (static build / serverless-функции).
- Источник данных: `public/news.json` (zero-touch контент-пайплайн Фазы 2).
- Репозиторий: GitHub (`main` — стабильные релизы, `dev` — интеграционная ветка).
- CI: GitHub Actions (quality-dev, verify, e2e-quick, Content Compliance, nightly).

## 3. Слоистая архитектура

Проект построен как 4-слойная система:

- `ui/`
  - React-компоненты, Tailwind, верстка и интеракции пользователем.
  - Нет прямых `fetch`, нет доступа к низкоуровневым API.

- `application/`
  - Прикладная логика, оркестрация сценариев.
  - Работа с bookmarks, режимами отображения, навигацией, вызовами инфраструктуры.

- `domain/`
  - Доменные типы и инварианты: `NewsItem`, `Category` и т.п.
  - Чистые структуры данных, независимые от UI/HTTP/платформы.

- `infrastructure/`
  - Работы с внешним миром: `api-client`, хранилища (localStorage), интеграция с Telegram WebApp, файловая система в скриптах.

Инварианты:

- `ui` → `application` → `domain`
- `ui` → `application` → `infrastructure`
- `domain` никогда не импортирует `ui`.
- `ui` не делает `fetch` напрямую.

## 4. Поток данных (контент-пайплайн → miniapp)

1. **Ingestion / normalize (Фаза 2)**

   - Скрипты в `scripts/*.cjs`:
     - `fetch-news-stub.cjs` / будущий реальный fetch — забирает новости из источников.
     - `normalize-news.cjs` — приводит сырой контент к контракту `news.json`.
     - `validate-news.cjs` / `dqm-validator.cjs` — проверяют схему и правила качества.
   - Результат: обновлённый `public/news.json` + запись SHA-256 в `docs/checksums/chain.log`.

2. **Delivery**

   - `news.json` разворачивается вместе со статической сборкой.
   - В проде miniapp читает `news.json` как статический ресурс, с учётом кеширования (ETag/Cache-Control).

3. **Клиентский код**

   - `src/infrastructure/api-client.ts`:
     - читает `news.json`;
     - валидирует данные по доменной/контрактной схеме;
     - отдаёт данные наверх в слой `application`.

   - `src/application/*`:
     - применяет фильтры/сортировки/закладки;
     - готовит данные к отображению.

   - `src/ui/*`:
     - рендерит карточки, списки, панель фильтров;
     - управляет TTS/режимами отображения.

## 5. CI / Quality / Observability (overview)

- **Основные проверки (L0/L1):**
  - `1) Verify (Lint + Types + Build + Tests + Audit + Size + LHCI)` — блокирующий gate для `main`.
  - `Content Compliance Gates` — блокирующий gate для контента и `news.json`.
  - `e2e-quick` — быстрые Playwright-сценарии.
  - `quality-dev` — набор проверок на `dev`.

- **Ночной контур (L2):**
  - Stryker — мутационное тестирование ключевых модулей.
  - k6 — базовый нагрузочный smoke.
  - OSV-Scanner, Semgrep, Gitleaks — безопасность.
  - Visual regression — Playwright + скриншоты.

- **Observability:**
  - Логирование через `reportError`/логгер (переход к структурированным логам).
  - Метрики контента (TTFPR, объём, дубли) собираются через `metrics-collector.cjs` (план).

## 6. Инварианты и красные линии

- Прод-контент (`public/news.json`) никогда не правится руками напрямую.
- Любые изменения данных проходят через:
  - ingestion → normalize → validate → Content Compliance → PR → merge.
- Любое изменение, нарушающее инварианты архитектуры, требует ADR.
## 4. Управление состоянием (State Management)

- Глобальный стор реализован в каталоге `src/store`.
- В нём хранятся долгоживущие UI-состояния приложения:
  - выбранные фильтры/теги;
  - состояние закладок (bookmarks);
  - режимы отображения ленты/чтеца;
  - флаги, влияющие на поведение TTS и т.п.
- Краткоживущий локальный стейт (`useState`) используется только для чисто локальных вещей:
  - состояние модалок, dropdown, временных input и т.п.
- Data-кэш (данные новостей) приходит через слой `infrastructure` (`api-client`) и используется в `application`/`ui`, но **не хранится в сторе как «сырое» состояние**.

Инварианты:

- Вся логика глобального UI-состояния сосредоточена в `src/store`.
- React-компоненты `ui` не создают свои «мини-глобальные стейты» поверх этого решения.

## State Management (Zustand)

Глобальное состояние приложения реализовано на базе Zustand:

- Код стора расположен в каталоге `src/store`.
- В сторах фиксируется долгоживущий UI-стейт:
  - выбранные фильтры и теги;
  - строка поиска;
  - сортировка ленты;
  - флаг отображения только закладок;
  - флаги и режимы TTS/чтения.
- Локальный `useState` используется только для чисто локальных вещей
  (модалки, временные поля ввода и т.п.).

Инварианты:

- Все глобальные UI-состояния проходят через Zustand-стор.
- Сырой data-кэш (`news.json` и его проекции) приходит через слой `infrastructure`
  и обрабатывается в `application`, но не превращается в «размазанный» глобальный стейт по компонентам.
