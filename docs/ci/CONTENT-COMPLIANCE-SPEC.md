# Content Compliance — Baseline Spec (Phase 2 / Step 0.6)

Статус-чек для PR, меняющих контент. Цель — не допустить некорректные данные и изменения вне allow-list.

## Allow-list файлов (для контент-PR)
- `public/news.json`
- (опц.) `data/news_raw.json`, `data/news_auto.json` — если будут использоваться промежуточные артефакты
- Никаких изменений кода/конфига/CI в контент-PR: **запрещено**

## Красная зона (BLOCK — PR не мержится)
- Нарушение JSON Schema (`docs/schema/news.schema.json`)
- Дубликаты (`id`, `url`, `title+date`)
- `date` не в UTC (`...Z`) / не парсится
- `url` не начинается с `https://`
- Наличие `<` `>` в `title`/`preview`
- Порядок не DESC по `date`
- Изменения файлов вне allow-list
- Слишком большой diff по `public/news.json` (порог соглашением; по умолчанию 500 KiB)
- Открыт второй контент-PR при незакрытом первом (конкурентность)

## Жёлтая зона (WARN — PR мержится вручную с особым вниманием)
- «Пустая прогонка» (0 новых записей), если это не ожидаемо по SLA источников
- Размер превышает «рекомендованный бюджет», но не утыкается в максимальный
- Ненормально высокий объём фильтрации дублей в парсере

## Дополнительные проверки (информативные)
- TTFPR (время от fetch до PR)
- Баланс новых/отфильтрованных записей
- Сводка источников (кто дал/не дал новости по SLA)

## Формат отчёта в PR
- Итог: ✅ PASS / ⚠️ WARN / ❌ FAIL
- Сводка: количество записей, дубликаты, размер, сортировка, UTC/HTTPS
- При FAIL — список конкретных причин с индексами и фрагментами

## Включение в Branch Protection
- Имя статуса: **Content Compliance**
- Required на ветке `main` (и `dev` — после финала Фазы 2)
