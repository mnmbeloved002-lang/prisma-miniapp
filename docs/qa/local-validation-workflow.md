# Local Validation Workflow — Phase 2 / Step 0.3

## Назначение
Единый регламент локальной проверки `public/news.json` перед любыми изменениями. Без ручных исключений.

---

## Входные данные
- Файл: `public/news.json`
- Формат: массив объектов (карточек)

## Критерии качества (инварианты)
1) **JSON-парсинг**: файл корректно парсится.
2) **Топ-уровень**: массив.
3) **Обязательные поля**: `id`, `title`, `date`, `url`, `tags`.
4) **title / preview**: строки; длины — `title: 10–180`, `preview: 0–240`; **запрещены** `<` и `>` (никакого HTML).
5) **tags**: массив `1..5`; каждый тег — строка `2..24`.
6) **date**: ISO8601 UTC, **обязательно** оканчивается на `Z` и валидно парсится.
7) **url**: начинается с `https://` (только HTTPS).
8) **Уникальность**: нет дублей по:
   - `id`,
   - `url`,
   - паре `title + date`.
9) **Порядок**: массив отсортирован по `date` **по убыванию (DESC)**.
10) **Пустой массив** допустим (0 элементов) — это не ошибка.
11) **Объём/перформанс**: до ввода бюджетов в шаге *1.5* временно контролируем, чтобы файл был разумного размера (до 1 МБ) и ≤ 1000 элементов.

---

## Что считается ошибкой (ломает приёмку)
- JSON не парсится / не массив.
- Нарушение любых правил п.3–9.
- Ссылки не `https://`.
- Даты без `Z` либо не парсятся.
- Дубликаты (`id`, `url`, `title+date`).
- Неверный порядок (не DESC).
- Наличие HTML (`<` `>`) в `title`/`preview`.

---

## Ожидаемые сообщения об ошибках (эталоны формулировок)
> До внедрения автоматического валидатора записываем **человеческие** формулировки, чтобы все понимали, что исправлять.

- `Top-level must be an array.`  
- `Missing required field: <field> (index N)`  
- `Invalid title length (expected 10..180, got X) (index N)`  
- `HTML is not allowed in title/preview (index N)`  
- `date must be UTC (end with 'Z') (index N)`  
- `Invalid date value: <value> (index N)`  
- `url must start with https:// (index N)`  
- `Duplicate id: <id>` / `Duplicate url: <url>` / `Duplicate title+date: "<title>" @ <date>`  
- `Array must be sorted by date DESC at indexes i -> i+1`

---

## Процедура локальной проверки (до появления скрипта)
1) Открыть `public/news.json`.
2) Визуально проверить 1–2 элемента на соответствие полям/диапазонам/UTC+Z/https.
3) Просмотреть начало и середину списка на монотонность DESC.
4) При любом сомнении — временно приводим к пустому массиву `[]` и считаем это **валидным** состоянием.

> На шаге *ЭТАП 1 / 1.3–1.4* будет добавлен авто-валидатор (скрипт и CI чек `Content Compliance`). Тогда локальная проверка будет выполняться командой `npm run validate:news`.
